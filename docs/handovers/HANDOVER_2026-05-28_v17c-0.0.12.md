## Background: how we got here

### The v17c design constraint (POM's framing in his original May 27 email)

- Reach IDs and Node IDs must stay constant v17b ↔ v17c (D0 ↔ D2 continuity).
- Lat/lon may be touched only via **"limited node location bug correction"** (canonical case: reach 35301100891).
- For nodes that are out-of-geographic-order relative to their IDs, the design intent is to encode the correction in the `node_order` column, **not** move lat/lon.
- POM: *"this option that was bugged around up to version 8 … was not used latter on, and is not used at all in version 17c official (beta 11). Instead, the concerned nodes in version 17c have been moved (lat-lon). In the long run (version 18) this is the correct way to do it, but in version 17c this implies that there will be a discontinuity in the time series."*

### Mode A vs Mode B (the key technical learning)

The detectors (N013, test 6b) are **symptom-blind to root cause**:

- **Mode A** — centerline-to-node mapping bug. All ~75 nodes in the reach are at wrong lat/lon, kilometers off the river. `rederive_nodes` (recompute lat/lon from centerline spatial partitioning) is correct.
- **Mode B** — reach mostly correct, 2–3 misplaced nodes. `rederive_nodes` overwrites positions that didn't need changing. **`node_order` patch** (encode geographic sequence over existing v17b lat/lons) is the right mechanism.

Jake used the Mode A tool on Mode B problems in 0.0.10. POM has been making this distinction since April 13 explicitly, and earlier implicitly. The reason it propagated: `rederive_nodes` was already built and proven in 0.0.8, so when the detector flagged more cases, extending the existing tool felt natural. The detector hid the failure-mode shift.

**Things to revert (full column set — verified against `rederive_nodes` at workflow.py:4920-4951):**

`rederive_nodes` mutates **more than just x/y/node_length**. To produce a clean revert, you must restore:

- `nodes.x`, `nodes.y` — coordinates (the obvious ones)
- `nodes.node_length` — segment length
- `nodes.cl_id_min`, `nodes.cl_id_max` — centerline ID range bounds (these define which centerline points belong to this node)
- `centerlines.node_id` — for affected centerlines, restore v17b's centerline → node assignment

Skipping `cl_id_min`/`cl_id_max` or `centerlines.node_id` will leave N013 (CL-node misallocation) failing because the spatial join becomes inconsistent.

**Things to preserve (do NOT revert):**

- **Midpoint `dist_out` convention** — separate 0.0.8 change (all 11.1M nodes shifted ~99 m mean) that POM accepted. Keep.
- **Lakeflag / type reconciliation** (0.0.11) — keep.
- **Node-order downstream-first ordering** in NetCDF — keep.
- **Metadata variables** restored in NetCDF (`river_name_local`, `river_name_en`, `version`, `add_flag`, `swot_obs_source`) — keep.
- **Flow correction = disabled** — keep.
- All other 0.0.11 state — keep.

**Reactive system note (IMPORTANT):** `src/sword_duckdb/reactive.py` only fires when changes go through the SWORDWorkflow / SWORD class API with `mark_dirty()`. **Raw SQL UPDATEs bypass it entirely.** If you do the revert via raw SQL (which is fine and how `revert_oc_reach_split.py` does it), do NOT expect any dependent fields to auto-recompute.

indexes = con.execute("""

con.execute("""

             WHERE v17b_n.node_id = nodes.node_id AND v17b_n.region = nodes.region),

con.execute("""

## Lessons learned (already logged to `.napkin.md`)

1. **Heuristic-driven scope expansion needs an explicit "is this still inside the agreed external envelope?" gate** before merging. The detector caught real problems AND over-caught.
2. **Detectors are symptom-blind to root cause.** N013 / test 6b flag the same shape for Mode A (centerline-mapping bug) and Mode B (a few mispositioned nodes). The right *fix* differs by root cause; the *detector* doesn't.
3. **Tool reuse past appropriate scope** is the failure mechanism. `rederive_nodes` worked correctly in 0.0.8 (Mode A). Reusing it in 0.0.10 on Mode B problems was the actual mistake — not "Jake ignored POM," but "Jake had the tool in hand and didn't switch mechanism when the failure mode changed."
4. **POM's understated register** ("for v18 I guess" = "do not do this in v17c") needs to be read as deferral, not as soft preference. Same with "probably for v18" — that's a constraint signal.
5. **Same-day-merge-with-collaborator-email-in-flight** is a danger pattern. POM's email arrived 1h25min before PR #225 merged. The cost of waiting 24h is ~zero; the cost of an unfixable scope expansion is a mapping table + a long apology.
